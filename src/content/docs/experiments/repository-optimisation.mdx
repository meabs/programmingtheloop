Does preparing a repository for coding agents improve correctness enough to justify the extra context and upkeep?

## Research question

Does a repository configured with generated knowledge and agent-operating aids help an agent complete code changes and answer structural questions more accurately or with fewer tokens than the same source without those additions?

## Prediction (written before counted runs)

I expected the code graph and the generated guide to pay for themselves on a 1,173-file Java monolith: fewer tokens on structure questions, because the graph answers caller and path questions in one call. I also half expected the agent to ignore the tools, and predicted it would read a skill file in fewer than half the runs. Predictions: [docs/EXPERIMENT_J.md](https://github.com/meabs/OKFExperiment/blob/main/docs/EXPERIMENT_J.md).

## Setup

Same 1,173-file Java backend in two conditions:

- **Plain:** source only — no `AGENTS.md`, generated guide, code graph or agent skills.
- **Prepared:** configured `AGENTS.md`; generated package guide; code graph (`kg callers`, `kg impact`, `kg subclasses`, `kg path`); three operating skills (navigate, change, check).

Four mechanical changes (one rename touched 105 sites in 58 files) and three structure questions. Eight repetitions per task and condition: **112 counted runs**. Agent: Codex with isolation on. Model recorded for findings 1–3: `gpt-5.6-luna` at medium reasoning.

## Results

| Task group | Plain | Prepared | Interpretation |
| --- | ---: | ---: | --- |
| Mechanical changes | 28/32 passed | 29/32 passed | p = 1.0; difference not reliable |
| Structure questions | 16/24 correct | 19/24 correct | p = 0.52; difference not reliable |
| Token use, task-weighted ratio | 1.00× | **1.48×** (bootstrap 1.38–1.60) | Prepared reliably cost more |
| Simple mean-token ratio | 297k | 401k (**1.35×**) | Lower than task-weighted because the big rename dominated totals (1,046k vs 1,278k per run; ratio 1.22) |
| Mean turns | 5.9 | 8.8 | Agent read instructions, guide and graph, *then* still searched source |

The agent ran the graph and opened the guide in all 56 prepared runs, and read the navigation skill in **55 of 56**. Structure questions used **1.56 times** more tokens on the prepared arm (ratio of the two arms’ mean tokens on the questions) — the opposite of the prediction. The foreword summarises finding 1 as **35–48% more tokens**, with no reliable correctness gain: 29 against 28 of 32 changes, 19 against 16 of 24 structure questions, both within noise.

The plain arm was already strong: **44 of 56** outcomes across the measured tasks.

Source: [results/J-optimised-repo.md](https://github.com/meabs/OKFExperiment/blob/main/results/J-optimised-repo.md).

### Grading correction (published with the results)

The first grader scored the hardest task 0 of 8 in both arms because it missed four strings every run had correctly updated. Re-scored: 4 of 8 against 6 of 8 ([docs/EXPERIMENT_J.md, Deviations](https://github.com/meabs/OKFExperiment/blob/main/docs/EXPERIMENT_J.md)).

## Limits

One repository, one model, mechanical edits and structure questions. Four ingredients tested together, so the study cannot say which one caused the extra cost. It does not establish what happens on other repositories, models or task types. Sample-size note from the book: J’s spread implied about **33 runs per arm** to detect a 20% cost difference; the trial used 8.

## Practical interpretation

**Engineering recommendation:** start with repository source and existing tools. Add a guide, graph or skill when a task exposes a specific information gap, and measure both correctness and cost before keeping the extra layer. This is recommendation informed by the result, not a finding that such tools never help.

See also [Chapter 3](/learn/right-facts/) for the dependency and stale-knowledge trials that flip the picture when the agent *cannot* read the code.
