<span class="experiment-status published">● &nbsp; PUBLISHED · FIRST EDITION</span>

Does preparing a repository for coding agents improve correctness enough to justify the extra context and upkeep?

## Research question

Does a repository configured with generated knowledge and agent-operating aids help an agent complete code changes and answer structural questions more accurately or with fewer tokens than the same source repository without those additions?

## Prediction

Before counted runs, the author expected the generated guide and code graph to pay for themselves on a 1,173-file Java monolith. The documented predictions included fewer tokens on structure questions and that the agent would read a skill file in fewer than half the runs. The predictions were recorded in `docs/EXPERIMENT_J.md` before counted runs.

## Experimental setup

The source was a 1,173-file Java backend. The same source was used in two repository conditions:

- **Plain:** repository source, with no `AGENTS.md`, generated guide, code graph or agent skills.
- **Prepared:** configured `AGENTS.md`; a generated package guide; a code graph with caller, impact, subclass and path queries; and three operating skills for navigation, code changes and verification.

The study included four mechanical changes (one rename affected 105 sites across 58 files) and three structure questions. It ran eight repetitions per task and condition: 112 counted runs in total. The agent was Codex with isolation on. The book identifies its model for findings 1–3 as `gpt-5.6-luna` at medium reasoning.

Across all runs, a simple ratio of mean tokens was 401k versus 297k (1.35×). That is lower than the task-weighted ratio because the rename across 58 files dominated total tokens and had one of the smallest per-task ratios, 1.22×. The prepared condition took 8.8 turns against 5.9. The agent ran the graph and opened the guide in all 56 prepared runs, read the navigation skill in 55 of 56, and still searched and read source code.

## Limitations

This was one repository, one model and a narrow set of mechanical edits and structure questions. Four repository ingredients were bundled, so the study cannot say which one caused the extra cost. It does not establish what happens on other repositories, models or task types. The plain arm was already strong: 44 of 56 outcomes across the measured tasks.

## Practical interpretation

**Engineering recommendation:** Start with repository source and existing tools. Add a guide, graph or skill when a task exposes a specific information gap, and measure both correctness and cost before keeping the extra layer. This is the author’s recommendation informed by the result, not a universal finding that such tools never help.
