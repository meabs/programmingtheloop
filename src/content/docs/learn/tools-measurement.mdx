<p class="chapter-kicker">Chapter 9 · web summary</p>

Boring tools win. An agent is only as useful as the tools it can reach, and the best ones are mostly fast, quiet command-line tools with clear errors. Specialised tools, such as a code graph, earn a place for specific question types rather than everywhere. Any change to your agent set-up should be measured with repeated runs and intervals — a single before-and-after tells you almost nothing.

## What makes a tool agent-friendly

Fast (an agent may call it dozens of times a session). Clear errors (the error message is the agent’s next prompt). Concise output. Hard to misuse. One command for one job, set-up included. Before building an integration, ask whether a ten-line script in `scripts/` would do.

## Skills

Evidence is mixed. The documentation-layer study (unpublished, lower-grade) found small skills discovered without prompting. Experiment J (published) found its three general operating skills were read (navigation skill in 55 of 56 runs) and the set-up still cost more with no reliable gain. Put a procedure in a script if you can. Create a skill only for a procedure that really does recur and that a script can’t carry.

## Code graph accuracy

For Java, call links checked against compiled bytecode: 13,380 of 13,380 high-confidence and 8,947 of 8,957 medium-confidence links correct on a large e-commerce backend (figures carried over from an earlier project, not re-derived). Python: 378 of 433 call edges whose caller ran (87%) observed at runtime in Click’s test suite. TypeScript/JavaScript: 32 of 32 sampled edges correct by hand. Built-in audit later: precision 100% on samples from Click and Express; recall 74% for Click and 18% for Express. Source: [AgentGraphWorkTree, docs/EVALUATION.md](https://github.com/meabs/AgentGraphWorkTree/blob/main/docs/EVALUATION.md).

## Measuring honestly

Agent runs are expensive and noisy. In one arm of one trial, runs on the same questions ranged from 55k to 3.0 million tokens ([docs/RESULTS.md, D1](https://github.com/meabs/OKFExperiment/blob/main/docs/RESULTS.md)). [AgentTrialRig](https://github.com/meabs/AgentTrialRig) reports each arm’s cost relative to a baseline with a bootstrap interval; under 8 runs per arm, verdicts are marked provisional. Expect to need **20 or more runs per arm to detect a 20% difference**. Experiment H1’s spread implied about 131 runs per arm; J’s, about 33.

### Agents use whatever they can reach

In one experiment the agent was not supposed to have the backend source, but Codex could read the whole disk. Three of 24 runs in the “no backend” arm searched it; one found another run’s generated guide; two found copies of the backend source ([docs/RESULTS.md, D1](https://github.com/meabs/OKFExperiment/blob/main/docs/RESULTS.md)). With network access on, 56 of 120 runs cloned the public repository from the internet; all 8 of the contract arm’s correct answers were among them (README, H2). Remedies: fresh clone per run, leak check, separate database per run, deny reads outside the work folder.

### Mistakes I made and kept

Early runs told the agent to verify in every arm, which hid differences — I reran them. Identifiers had to be renamed so agents couldn’t answer from learned knowledge. In J, the first grader scored the hardest task 0 of 8 in both arms because it missed four strings every run had correctly updated; re-scored, it was 4 of 8 against 6 of 8. One contaminated run is archived and unreported.

The worked example’s 9-test suite was coupled to the hand-written implementation, so even correct agent runs passed only 3 of 9. The live check and a 7-check black-box behaviour test were the independent measures in the trials.

## Recommendation

Prefer plain CLIs and small scripts. Make them fast, quiet and clear in their errors. Add specialised tools for the question types where they’ve been shown to help. Before keeping any change to your set-up, measure it: real tasks, several runs per arm, fresh clones, intervals, and a monthly re-run.

## Checklist

- [ ] Prefer plain CLIs and small scripts to bespoke integrations.
- [ ] Fast, quiet, clear errors, hard to misuse; one command per job.
- [ ] Specialised tools for the questions they help; not everywhere.
- [ ] Check a tool’s accuracy before trusting its output.
- [ ] Measure set-up changes with repeated runs and intervals.
- [ ] Fresh clone per run; check no run can reach another’s files, or the network.
- [ ] Publish your mistakes and re-scores with your results.
