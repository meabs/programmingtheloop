You’re the first reviewer of anything your agent produces. Size that review to the *consequence of being wrong*, whatever the size of the diff or the confidence of the description. I judge that consequence on three criteria: **reversibility**, **blast radius** and **verification strength**. Strong verification can lower the review a change needs; weak verification raises it, whatever the size.

I haven’t measured these tiers; they’re a suggestion.

## Risk tiers (illustrative)

| Tier | Typical change | Review |
|---|---|---|
| **Low** | Docs, test additions, mechanical refactors with a checker, dependency patches with green CI | Automated checks plus model review; human optional *if* your evidence supports it |
| **Medium** | Feature work inside one service, behind tests | Model review plus a human read of the evidence and the diff |
| **High** | Data model or public contract changes, cross-service changes | Plan agreed before coding; human review of every line; contract and integration checks |
| **Critical** | Security, authentication, money, permissions, deployment, data deletion | Constrained execution; explicit human decision points; negative-path tests; rollback plan; independent review |

A change can move up a tier during review if it turns out to touch something sensitive. Move down only when you have evidence that the lower tier is safe.

## Worked example, stage 7

Review in this order: brief, evidence, shape of the diff, tests, implementation, tier. Evidence before code.

The availability change touched three files, 121 insertions, all inside the brief’s scope. Tests covered all four criteria and included a test that parses the contract’s own example. Errors are surfaced, not swallowed. Tier: **Medium** — additive endpoint, reversible by revert, one service, strong verification including real use. If it had changed the contract, it would be **High**.

## How much human review?

Simon Willison: don’t file pull requests with code you haven’t reviewed yourself — description included. Keep diffs reviewable; never mix structural and behavioural changes in the same commit (Kent Beck). My position: review everything until your verification is strong enough to show, with evidence, where skipping human review is safe. Then tier by risk. That is a recommendation; I haven’t measured review policies.

A different model as reviewer is a filter, not a verdict. Watch for recreating things that already exist, inappropriate abstractions, scope creep, weakened tests, swallowed errors and unasked-for dependencies.

## Checklist

- [ ] Review your own agent’s PR first, description included.
- [ ] Grade by reversibility, blast radius and verification strength, not size.
- [ ] Evidence before code; tests before implementation.
- [ ] Keep diffs small; structural and behavioural changes in separate commits.
- [ ] Use a different model as a filter, not a verdict.
- [ ] Move a kind of change down a tier only on evidence.
