Chapter 3 is the book’s central evidence chapter. Its results do not support a rule that more context is always better. The useful question is whether relevant, authoritative facts are available at the point they are needed.

## Measured findings

**Experiment J — repository optimisation.** On a 1,173-file Java monolith, the prepared repository combined a generated guide, code graph, three operating skills and configured `AGENTS.md`. It used 35–48% more tokens, with no reliable correctness gain in the tested tasks: 29 versus 28 of 32 changes and 19 versus 16 of 24 structure questions, both described as within noise. The question-level token ratio was 1.56 for structure questions; on the rename task totals were 1,046k and 1,278k tokens per run. **Limits:** one repository and model, mechanical edits and structure questions, 8 runs per task per arm, four ingredients tested together. Source identified in the book: OKFExperiment, `results/J-optimised-repo.md`.

**Missing dependency knowledge.** A storefront change depended on an unseen backend. With no backend facts, 3 of 20 runs passed hidden tests; with a backend guide, 19 of 20 small-task runs and 18 of 20 harder-task runs passed. A later comparison found an API contract or a 3 KB note did about as well, more cheaply. **Limits:** five runs per task, identifiers renamed by the author, one model. Source identified in the book: OKFExperiment, `docs/RESULTS.md`, sections F and G.

**Stale dependency knowledge.** When four names in a backend were changed, agents using a stale guide and unable to inspect source repeated old answers in 14 of 16 drift answers. None of the wrong answers hedged. **Limits:** planted drift, four runs per question, one model. Source identified in the book: OKFExperiment, `docs/RESULTS.md`, section D2.

## What to take from this

**Engineering recommendation:** Prefer the smallest authoritative fact that closes a real information gap, and make its source and freshness visible. The experiments describe specific tasks; they do not establish that every graph, guide or instruction file is wasteful.

**Open question:** How much of these effects carry across other repositories, tasks, models and harnesses? The first edition does not answer that broadly.

## Try this

Before creating a context artifact, write down the inaccessible fact it supplies, how the agent can verify it, and who will update it. Compare a concise contract or note with a larger generated knowledge layer only when the task and evaluation are held constant.

## A layered approach from the chapter

When the agent can read a repository, the book recommends relying on source and existing tools, with an instruction to confirm facts in source. For an unreadable dependency, start with a versioned, provider-owned API contract covering success and error responses. Add a short owned note for conventions a contract cannot carry. Add structural guides or graphs only for tasks that need call relationships; put business behavior in tests. Gate supplied knowledge on freshness, while remembering a version check cannot prove behavioral compatibility.

The recommended starting point is no extra generated layer and a short `AGENTS.md`. Add the smallest authoritative context only when a real task requires it. The freshness scripts described in the book were small examples, not a demonstrated real production pipeline.
