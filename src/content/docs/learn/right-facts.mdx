<p class="chapter-kicker">Chapter 3 · web summary · heart of the book</p>

An agent working in a repository it can read should mostly be left to read it. Adding generated guides, graphs and long instruction files on top tends to add cost without adding correctness. An agent working across a boundary it *can’t* see needs facts, and those facts decide whether it succeeds. Supply them as the smallest authoritative thing that will do — usually a versioned contract, then a short owned note — and check freshness *outside* the knowledge itself. This is the chapter to read if you read only one.

## When the agent can read the code

**Experiment J** compared a plain 1,173-file Java backend with the same source prepared for agents: configured `AGENTS.md`, a generated package guide, a code graph (`kg callers`, `kg impact`, `kg subclasses`, `kg path`) and three operating skills. 112 counted runs: four mechanical changes (one rename touched 105 sites in 58 files) and three structure questions, 8 runs per task per arm, Codex with isolation on. Model for findings 1–3: OpenAI’s Codex recorded as `gpt-5.6-luna` at medium reasoning.

| | Plain | Prepared |
|---|---:|---:|
| Mechanical changes passed | 28 of 32 | 29 of 32 (p = 1.0) |
| Structure questions correct | 16 of 24 | 19 of 24 (p = 0.52) |
| Token use (task-weighted ratio) | 1.00× | **1.48×** (bootstrap interval 1.38–1.60) |
| Simple mean-token ratio | 297k | 401k (**1.35×**) |
| Mean turns | 5.9 | 8.8 |

The agent ran the graph and opened the guide in all 56 prepared runs, read the navigation skill in 55 of 56, and still searched and read the Java source. The extra layers sat on top of source navigation; I paid for both. Foreword finding 1 phrases the same result as **35–48% more tokens**, with no reliable correctness gain.

**Limits:** one repository, one model, mechanical edits and structure questions, 8 runs per task per arm, four ingredients tested together. The plain arm was already strong: 44 of 56. Source: [results/J-optimised-repo.md](https://github.com/meabs/OKFExperiment/blob/main/results/J-optimised-repo.md), [docs/EXPERIMENT_J.md](https://github.com/meabs/OKFExperiment/blob/main/docs/EXPERIMENT_J.md). Predictions were written before counted runs; I expected fewer tokens on structure questions and that the agent would read a skill in fewer than half the runs. Both were wrong (structure questions used 1.56× more tokens).

A smaller library (Click) said the same earlier: agents answered 14 or 15 of 15 questions and made 8 or 9 of 9 changes correctly with or without a guide; the default guide cost 1.30× tokens in one run and 1.07 in a rerun ([docs/RESULTS.md, section A](https://github.com/meabs/OKFExperiment/blob/main/docs/RESULTS.md)).

### Documentation layout (lower-grade evidence)

A separate study compared documentation layouts on six copies of one FastAPI and React application. It is my own unpublished document, so its evidence is **lower grade** than the rest of this chapter — you can’t check its numbers against a public repository. I use it for the *shape* of a layer. The heavy design (long always-read `AGENTS.md`, decision records, OKF pages) was dearer on the simple change in all four rounds: **+40.3% tokens**, +28.7% cost. With prompts that never mentioned the documentation, the lean design (19-line `AGENTS.md` index plus task-scoped skills) was discovered in **24 of 24** measured cells. Over eight rounds, lean was cheaper than baseline in 7 of 8 rounds on both change tasks (two-sided binomial p = 0.07): suggestive, not confirmed. On five other open-source repositories, one run per cell, three of five generated layers contained a task-relevant factual error.

**Optimising the layout of knowledge is a different question from whether the knowledge was needed.** Where J and the layout study pull in different directions, this book follows J (published and checkable).

## When the agent can’t read a dependency

On a React storefront whose Java backend was unavailable (identifiers renamed so the agent couldn’t answer from learned knowledge):

- Tracing questions with nothing: **1 of 24** correct, about **785k** tokens per question searching then giving up ([docs/RESULTS.md, D1](https://github.com/meabs/OKFExperiment/blob/main/docs/RESULTS.md)).
- Cross-repository change tasks graded by hidden tests: with nothing, **3 of 20** passed; with a guide to the backend, **19 of 20** (small tasks) and **18 of 20** (harder tasks), level with an agent given the backend’s real source (18 of 20) (sections F and G). Where the name wasn’t guessable, agents with nothing passed **0 of 30** across F and G.

**Limits:** 5 runs per task, identifiers renamed by me, one model.

**Experiment H** (harder change tasks, five arms, 16 runs each): nothing, OpenAPI contract, hand-written 3 KB note, generated guide, and source. All four beat nothing (4 of 16) and didn’t differ reliably from each other: contract 13, note 14, guide 14, source 14 of 16. The note was cheapest at about 128k tokens per run, against 192k for the contract, 282k for the guide and 334k for the source ([results/H1-contract-vs-okf-changes.md](https://github.com/meabs/OKFExperiment/blob/main/results/H1-contract-vs-okf-changes.md)). Caveats: I wrote the note knowing the tasks; the contract was generated from the source by a script. With 16 runs per arm, gaps under about 30 points can’t be separated.

## When the knowledge is out of date

**Experiment D2.** After I renamed four things in the backend, agents with the stale guide and no source to check gave the old answer in **14 of 16** drift answers; “read the source to confirm” or expiry dates on the changed concepts made no difference (16 of 16 each) because there was no source to confirm against. **None of the 46 wrong answers hedged.** Unchanged facts stayed correct (16 of 16 controls). Where the agent *could* read the code, “read the source to confirm before you rely on it” cut stale answers from 8 of 12 to 0 of 12 at the same cost (section B3). Confidence labels and warning banners did not prevent stale answers. The drift was planted, so this says nothing about how often drift happens in real pipelines. Source: [docs/RESULTS.md, D2](https://github.com/meabs/OKFExperiment/blob/main/docs/RESULTS.md).

## Code graph (route by question type)

On [AgentGraphWorkTree](https://github.com/meabs/AgentGraphWorkTree): for multi-hop “callers of callers”, the graph cut tokens sharply (Codex 84k against 196k; Cursor 121k against 414k; Copilot 161k against 181k). For simple lookups it was level or up to 80% dearer. Across 192 runs it did not reduce tokens overall — agents ran `kg` and then checked with `grep`. A graph earns its place for multi-hop structural questions; it costs extra as a general-purpose layer. Source: [docs/EVALUATION.md](https://github.com/meabs/AgentGraphWorkTree/blob/main/docs/EVALUATION.md).

## Worked-example agent trials (finding 4’s setup)

On the availability task, Cursor’s `composer-2.5`, 6 runs per arm: without the contract, black-box behaviour 0 of 6 and live check 0 of 6; with the contract, behaviour 6 of 6 and live check 4 of 6 as written (6 of 6 with the agent’s own URL variable set). Mean tokens 719k without vs 322k with. Without the contract every run wrote its own and guessed the path wrong. Fisher’s exact test on behaviour pass rates: p ≈ 0.002. **Limits:** one model, one task; two pilot runs excluded. What the agents *reported* (including rewriting the freshness gate) is in Chapter 5. Source: [agent-trials/results.md](https://github.com/meabs/ProgrammingTheLoop-WorkedExample/blob/main/agent-trials/results.md).

## Recommendation: a layered approach

1. If the agent can read the repository, rely on source and existing tools; add “read the source to confirm before you rely on it”.
2. For a dependency it can’t read, supply a **versioned API contract** first (provider-owned), listing every success and error response.
3. Add a short, owner-written note for what a contract can’t carry.
4. Add structural knowledge (guide, graph, or source) only for tasks that need internal call relationships.
5. Put business behaviour in tests and specifications.
6. Make freshness a gate outside the knowledge. A version check catches declared change only.

Start with nothing added and a short `AGENTS.md`. Never add a generated layer to a readable repository without measuring it on your own tasks.

## Checklist

- [ ] If the agent can read the code, let it; add “read the source to confirm”.
- [ ] Keep `AGENTS.md` a short index; procedures in scripts first.
- [ ] For code it can’t read: versioned contract first, then a short owned note.
- [ ] Add structural knowledge only for structural questions.
- [ ] Make freshness a pipeline gate; labels and banners don’t catch drift.
- [ ] Verify any generated documentation against the repository before trusting it.
- [ ] Measure every layer on your own tasks before keeping it.
