Chapter 4 follows the worked inventory change through orientation, facts, client, red test, implementation, real use and reporting. The progression makes prerequisites explicit before code changes begin.

## Close the loop

The chapter recommends one verifiable change per iteration, keeping state in files rather than relying on the model to remember it. The workflow should stop when a prerequisite is missing or a required branch cannot be verified; a plausible implementation is not a substitute for an unresolved dependency.

## Try this

Split a task into changes that each have a clear expected behavior and a runnable check. Write down stopping conditions and branches that require external access. Keep the task state, commands and observed results in the repository or run record.

## Chapter checklist

- Keep one verifiable change per loop iteration and store task state in files.
- Write the failing test first, then inspect which tests did not fail.
- Size each step so its check runs in minutes; use scripts or codemods for deterministic work.
- Before unattended work, define success, failure, danger and budget conditions.
- Stop on contradictions, destructive operations or out-of-scope changes; work on a branch and commit each completed step.
