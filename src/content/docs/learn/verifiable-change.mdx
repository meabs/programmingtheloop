Hand an agent one change you can verify at a time. A whole feature is too big a unit. Every agent runs the same loop — plan, act, observe, verify — whether you watch it or not. The quality hangs on two levers you control: how big each step is, and how good the verify step is. This chapter is about the first; Chapter 5 is about the second.

## Worked example, stage 4

The availability change as a single loop. The commands and their output are real (from the worked example’s `reproduce.sh`); the sequencing shows how an agent should work.

| Step | Reads | Changes | Checks |
|---|---|---|---|
| 1. Orient | `AGENTS.md`, brief, main, catalogue client, tests | Nothing | `bash scripts/test.sh`: contract fresh, 2 passed |
| 2. Facts | Contract 2.1.0 | Nothing | Path `/v2/stock/{sku}`, fields `on_hand`, `reserved` |
| 3. Client | Catalogue client as pattern | Adds inventory client | Test that parses the contract’s own example |
| 4. Red | Acceptance criteria | Adds availability tests | New endpoint tests fail |
| 5. Green | The failures | Adds the route | All tests pass |
| 6–7 | — | — | Live use and report (Chapter 5) |

On the red run, four tests failed and three passed. Two of the passes were 404 cases that passed because the route didn’t exist yet — FastAPI returns 404 for an unknown path. They prove nothing at that point. That’s what a red run is for: it shows which tests can’t fail.

Each step was small enough to check in seconds, and every check was a command rather than a judgement call.

## Putting the prerequisite in the command

In one AgentTrialRig trial, agents doing a FastAPI change kept tripping over the same set-up: the test database had no tables until migrations ran. Writing the step into `AGENTS.md` helped, but some agents still ran the tests first. A one-command test script that applied the migrations itself removed the problem in every run of that arm. Chapter 5 has the numbers. A step that must always happen belongs in a command. Three runs per arm gives a direction, not a measured saving.

Keep that command where the agent can’t edit it: Chapter 5 shows agents rewriting it to pass.

## Recommendation

Before handing over a task: can “done” be stated as a check that runs in a few minutes? Will the diff be something you can actually review? Can you throw the whole thing away without tears?

Before letting anything run unattended, write down success, failure, danger and budget conditions, and enforce them in the harness where you can. Work on a branch and commit each completed step.

## Checklist

- [ ] One verifiable change per loop iteration; state in files, not in the model.
- [ ] Write the failing test first and read which tests *didn’t* fail.
- [ ] Size each step so “done” is a check that runs in minutes.
- [ ] Any stage can stop the line; never auto-retry a defect away.
- [ ] Scripts and codemods for deterministic work; agents for judgement.
- [ ] Success, failure, danger and budget conditions before going unattended.
- [ ] Branch, and commit every completed step.
