This chapter is groundwork: what a coding agent is, how the evidence sits, and the worked example we follow through the book. The thesis is in the foreword; the rest of the book tests it a chapter at a time.

Speed was never the problem I wanted to solve. Agents already type faster than any of us. I wanted to stop them being confidently, plausibly wrong — writing against guessed APIs, trusting stale documentation, or reporting “all tests pass” when the suite never ran.

## What a coding agent is

Simon Willison’s definition is the cleanest: agents run tools in a loop to achieve a goal. The agent reads files, runs commands, edits code, looks at the result and decides what to do next, until *it* judges the goal met. That last part is the trap. A chatbot hands you text. An agent acts, and checks in when it thinks it’s finished.

So the questions that matter are: what does the agent know when it starts, how does it find out the rest, and how do you and it know when the work is actually done?

## The evidence, in outline

The experiments live in four repositories: [OKFExperiment](https://github.com/meabs/OKFExperiment) (about 1,650 controlled runs), [AgentTrialRig](https://github.com/meabs/AgentTrialRig), [AgentGraphWorkTree](https://github.com/meabs/AgentGraphWorkTree) and [AgentFrictionLoop](https://github.com/meabs/AgentFrictionLoop). The headline results are in the foreword and analysed in Chapter 3:

- Where the agent can read the code, extra knowledge mostly adds cost, not correctness (finding 1).
- Where it can’t, the right facts decide the outcome (finding 3).
- Out-of-date facts get repeated as fact, without hedging (finding 2).
- Executable checks beat prose: when a test prerequisite moved from a sentence in `AGENTS.md` into a script, agents stopped tripping on it (Chapter 5).

Those are findings, with limits given where each is introduced. What follows from them is labelled as recommendation.

## The worked example

One change runs through the book: add `GET /products/{sku}/availability` on a `storefront-api` whose stock numbers come from an `inventory-service` the agent cannot see. It is a reproducible demonstration of the failure modes the experiments found — guessed facts, stale knowledge, unverifiable claims — not a recorded agent session. Published at [meabs/ProgrammingTheLoop-WorkedExample](https://github.com/meabs/ProgrammingTheLoop-WorkedExample). The worked example’s code was written by hand; every test run, `curl` response and friction record shown in the book is genuine output of its scripts.

Separately, real agent trials on the same task (12 runs of Cursor’s `composer-2.5`, with and without the contract) are reported in Chapters 3 and 5.

## Recommendation

Before you adopt any agent practice, including mine, ask three questions: what facts does this give the agent that it couldn’t get for itself? How will the agent prove its work with something that runs? And what will this cost to maintain?

Distrust any claim based on a single run, including your own. In one of my trials, run-to-run spread was large enough that about 131 runs per arm would have been needed to detect a 20% cost difference; the trial had 16 ([results/H1-contract-vs-okf-changes.md](https://github.com/meabs/OKFExperiment/blob/main/results/H1-contract-vs-okf-changes.md)).

## Try this on your repository

1. Pick three recent small tasks: one bug fix, one feature, one refactor.
2. For each, write one line naming what the agent would need that it *can’t* find by reading the repository.
3. Write how the agent would prove the change with a command that runs. If there is no such command, note that too.
4. The first list is your real context problem; the second is your real verification problem.

## Checklist

- [ ] Use an agent that can run tools for real work, not a chat window alone.
- [ ] Own every line the agent writes.
- [ ] Before adopting a practice, ask: what facts, what check, what upkeep?
- [ ] Distrust single runs, including your own.
