The book opens by separating facts about a repository from mechanisms that check behavior. Both can help an agent; both need to stay connected to the code they describe.

## Three questions before adding a practice

Chapter 1 asks practitioners to identify the problem a practice addresses, the evidence that it helps, and the cost of keeping it current. That framing applies to generated guides, repository instructions, code maps and test harnesses.

The author also warns against trusting a single run. In one trial, observed spread implied about 131 runs per arm would be needed to detect a 20% cost difference; the trial had 16. This is the estimate for that trial’s variance and design, not a general sample-size rule.

The source presents a worked example that follows across the book: a storefront needs to expose inventory supplied by a separate backend. The boundary matters because an agent changing one repository cannot infer authoritative behavior from an unavailable dependency.

## Try this on your repository

For each instruction or generated artifact an agent reads, record its owner, source of truth, update trigger and consequence if stale. For each check, name the behavior it protects and whether it observes the real system or only a local substitute.

**Engineering recommendation:** Treat context and checks as maintained engineering assets. This is a recommendation from the book, not a universal measured effect for every repository.

## Chapter checklist

- Use an agent that can run tools for real work, and own every line it writes.
- Before adopting a practice, ask what facts it supplies, what runnable check proves the work and what upkeep it creates.
- Distrust single-run claims, including your own.
