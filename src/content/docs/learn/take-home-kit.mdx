Teams don’t need a knowledge platform before they get value from coding agents. They need a well-engineered repository with a short `AGENTS.md`, runnable checks, authoritative contracts for the things agents can’t read, and a habit of adding each further layer only when it has shown it pays. That is a recommendation, built on the findings in Chapters 3 to 9 and on engineering judgement where they run out.

If you strip the book back to three rules for Monday morning:

1. **Put the fix in a script, not a sentence.** Prose is advice; a script is law — and run it where the agent can’t edit it.
2. **Starve the local context; feed the boundaries.** Leave readable repositories alone. Spend documentation effort on edges the agent cannot see.
3. **Never trust a green report without an independent check.** Agents will rewrite a gate to agree with their guesses and still match the command log.

## Default, Conditional, Experimental

These labels are an **adoption framework**, not a statistical grade of evidence. They say how to adopt a practice in a typical team — how cheap, how reversible, how broadly it applies — not how strong the proof is.

| Label | Meaning | Decision rule |
|---|---|---|
| **Default** | Cheap, reversible, useful almost everywhere | Do it unless your repository gives a reason not to |
| **Conditional** | Pays off for certain repositories, tasks or sizes | Adopt after a targeted trial on your own work |
| **Experimental** | Promising; costs or benefits unproven in a team setting | Pilot separately, with an exit test |

**Default examples:** source/contracts/tests/CI as authoritative; short `AGENTS.md` as an index; briefs with acceptance criteria; one verifiable change per step; one-command checks run where the agent can’t edit them; versioned provider-owned contracts; honesty about *not run*.

**Conditional:** task-scoped skills (only where a script can’t carry the procedure — Experiment J’s general operating skills added cost); a code graph for multi-hop structural questions; a guide or note for facts across a repository boundary; parallel agents (on isolation).

**Experimental:** friction reporting and a weekly review; a full freshness pipeline beyond a cheap gate.

## Adoption path

| Stage | Implement | Move on when |
|---|---|---|
| **0. Baseline** | Reliable build/test/lint; short `AGENTS.md`; briefs | A fresh agent runs the core checks and makes a small change with reviewable evidence |
| **1. Targeted reuse** | Prerequisites in scripts; a skill only for high-friction procedures that still fail without one | Friction for that procedure drops; tokens per task don’t rise |
| **2. Cross-repository integrity** | Provider-owned contracts; pins; freshness gate; contract tests | A representative cross-repository change passes; a stale pin is caught |
| **3. Navigation pilot** | Optional graph for multi-hop questions; a guide only for code the agent can’t read | Your own trial shows a net saving without loss of quality (J’s full set-up failed this on a readable repository) |
| **4. Feedback pilot** | Friction notes, grouping, human PR loop | A repeated cause drops after its fix |
| **5. Scale decision** | Reuse across repositories | Cost and maintenance stay justified |

My experiments don’t justify a knowledge platform, a graph database or a documentation programme as a starting point.

## Kit templates (change every line to fit)

The worked example’s `AGENTS.md` is seven lines: source and tests authoritative; one check command; follow the catalogue client; inventory not in workspace; contract pinned and not editable; report commands and what you could not verify.

Also in the chapter: task-brief template, status-line format, friction one-liner, freshness-gate notes (version check only — not behavioural compatibility), and review grading by the Chapter 8 criteria.

## Three team checklists

**Before a task**

- [ ] Goal, acceptance criteria and out-of-scope are written down, or explicitly marked unresolved.
- [ ] The agent has a one-command check and the exact dependency versions it needs.
- [ ] The work is broken into independently verifiable steps.

**Before a pull request**

- [ ] Checks, including a real-use exercise, have been run, or are marked *not run* with a reason.
- [ ] The status line matches the command log, and correctness was judged by a check the agent didn’t write.
- [ ] Any diff to the gate, test script or tests has had human review.
- [ ] Every interface change has an owner and a compatibility decision.
- [ ] Any supplied knowledge was fresh against the dependency version in use.
- [ ] The change is graded and reviewed for its tier.

**Before adding any new agent infrastructure**

- [ ] There is a concrete repeated failure, or costly task, that it would prevent.
- [ ] It can’t be enforced more reliably as code, a test, a script or a schema.
- [ ] It has an owner, a freshness mechanism and a retirement date.
- [ ] You will measure it on your own tasks, and remove it if it doesn’t pay.

## Try this

Run Stage 0 this week. Give a fresh agent, in a fresh clone, a small real task with a written brief, and nothing else added. Write down every place it stalled. Build your adoption plan from that list.
